# EmuFusion engineering handover — 2026-08-07

This document is the authoritative handover for the next engineer or AI working
on EmuFusion. It records the intended product, what is actually implemented, what
has been proven on the AYN Thor, what has only passed local/static tests, what
has failed, why the architecture looks unusual in a few places, and the exact
order in which work should resume.

Do not infer completion from a core loading a ROM. A system is complete only
after the real EmuFusion menu, physical controller, in-window renderer, audio,
input, held-Stop return, save, restore, process-death, performance, legal,
reproducibility, and exact-APK gates all pass.

## 1. Executive status

EmuFusion is intended to be one Android application that combines:

- the credited Pegasus Frontend library/UI foundation;
- the EmuFusion theme and navigation system;
- library discovery and Downloads importing;
- title normalization and generated metadata;
- box-art, wallpaper, and preview-video enrichment;
- preview playback on one-screen and dual-screen hardware;
- application/theme updating;
- an in-app browser and background downloads;
- controller and AYN LED integration;
- Lucent-owned, in-process emulation;
- Quick Resume and automatic checkpoint history.

The product requirement is one app, one display-0 task, one display-0 Activity,
and one display-0 application window. Selecting a supported game from EmuFusion
must replace the library visually with gameplay inside the already-running
EmuFusion `MainActivity`. It must not launch RetroArch, a standalone emulator APK,
another Android task, another display-0 Activity, or an emulator menu. Exiting
must reveal the exact existing library state without reloading QML.

The work is at a safe stopping point:

- The user-approved menus are frozen and were not changed during the recent
  emulation work.
- A new immutable diagnostic/qualification APK has been built.
- Every local test and exact-payload verifier for that APK passes.
- The newest N64 held-Stop surface/save race has been fixed structurally in
  source and packaged.
- That newest APK has deliberately not been installed on the Thor, because the
  user requested a clean stop and handover instead of beginning another long
  device matrix.

## 2. Non-negotiable product requirements

These requirements came directly from repeated user feedback. Do not weaken
them to make a test pass.

1. **Do not touch or redesign the current menus.** The user considers the
   current Cover, List, System, and All Systems views correct. Recent work kept
   them byte-identical.
2. **All normal emulation must happen inside EmuFusion.** No external emulator
   app, emulator launcher, emulator menu, second display-0 Activity, or second
   recents entry is acceptable.
3. **The library must launch the emulator.** Direct-intent or qualification-
   Activity tests are useful diagnostics but do not count as acceptance. The
   accepted test is: navigate the real EmuFusion menu with physical controls,
   highlight a game, and press physical A.
4. **Return must be instant and exact.** Holding the Thor Stop/Select button for
   one second must reveal the same view, system, category/sort, scroll position,
   and selected game without a EmuFusion/Pegasus/loading/progress screen.
5. **Saving may complete after the library is visible, but it may not be
   skipped.** The current game must be quiesced safely, normal save RAM flushed,
   and a validated Quick Resume snapshot atomically committed.
6. **Tap versus hold behavior matters.** A short Stop/Select press remains the
   Select button. A continuous one-second hold exits gameplay.
7. **No RetroArch frontend.** EmuFusion implements the open libretro API itself.
   RetroArch menus, settings, assets, configuration, terminology, or package
   are not used.
8. **No visible emulator configuration.** EmuFusion chooses tested profiles.
   Normal users see play, remap controls, restore an earlier checkpoint, and
   exit—not core options.
9. **Dual-screen systems must use the Thor correctly.** DS and 3DS require top
   gameplay on display 0 and lower gameplay/touch on display 4. Wii U must do
   the same when Phase 3 reaches Cemu. Single-screen systems blank the lower
   gameplay display.
10. **Do not bundle games, commercial firmware, encryption keys, or console OS
    files.** User-supplied firmware must be hash-validated. Unsupported content
    must fail clearly and safely.
11. **Do not silently install emulator APKs.** The final architecture packages
    approved engines inside EmuFusion. Android also prevents a normal app from
    silently installing third-party APKs.
12. **Do not call a phase complete from build success alone.** Exact real-menu,
    physical-device proof is mandatory.

## 4. What EmuFusion currently contains

### 4.1 Distribution model

There are two intended deliverables:

1. **EmuFusion App APK.** The full experience: frontend, fixed EmuFusion theme,
   importer, media service, preview service, updater, browser, hardware
   integration, and approved internal engines.
2. **EmuFusion standalone theme ZIP.** A visual theme for an existing Pegasus
   installation. A QML theme alone cannot scan Downloads, write shared storage,
   update an APK, drive Thor LEDs, or host native emulator cores. Those features
   require the EmuFusion app.

Pegasus is credited in About, licensing, source offer, and third-party notices.
The user-facing product is EmuFusion. Internal Pegasus class names remain where
binary/JNI compatibility requires them.

### 4.2 Library views and navigation

The frozen theme provides:

- **Cover View:** horizontal system hardware/card presentation, followed by
  vertically reachable library shelves.
- **List View:** systems on the left and the active game/category list on the
  right.
- **System View:** one system's games with list and cover layouts.
- **All Systems View:** the same game experience over an aggregate library,
  with per-game system identity, logo, and accent changes.
- Seven categories/sorts: **Continue**, **Most Played**, **Recently Added**,
  **Critics**, **Users**, **A–Z**, and **Release**.
- Search with a magnifier-only closed state, expanded text field, clear X,
  Android keyboard, and controller navigation after the keyboard closes.
- Long-press game actions for rename, permanent ROM deletion, and category-
  specific “remove from list.” Removal is available only for Continue, Most
  Played, and Recently Added; it never hides a game from the complete Critics,
  Users, A–Z, or Release views.
- Touch dismissal outside settings and game-action sheets.
- Controller help text and view labels.

Important navigation semantics already encoded in the theme:

- L1/R1 change categories or sorts.
- L2/R2 change systems.
- Left/right page through lists where applicable.
- Up/down select rows.
- Y toggles layout.
- X opens settings.
- B returns from a selected game column to the systems list or exits the
  current view as appropriate.
- Configurable right-stick view switching maps up to Cover View, down to List
  View, and left/right through All Systems and individual System views.
- Trigger presses are tracked separately so reversing L2/R2 direction does not
  consume the first press.

### 4.3 Performance and preload behavior

The theme maintains a library index and per-system caches instead of rebuilding
and sorting the whole game model on every navigation event. It preloads adjacent
system logos, box art, wallpapers, and preview-video sources. All Systems uses
precomputed aggregate models. System caches are updated off the immediate input
turn, and visual selection moves immediately while slower preview work settles
on short timers.

This work was motivated by visible flicker and multi-second All Systems/system
switch delays. The current menu behavior is frozen because the user reported it
as correct. Any future performance change must preserve visible ordering,
selection, and the frozen hashes unless the user authorizes UI edits.

### 4.4 Visual identity and artwork behavior

Implemented theme policy includes:

- EmuFusion branding, with Pegasus attribution confined to About/licensing and the
  “powered by” credit rather than presented as a second app.
- Only platform-family logos represented by systems actually in the library.
- All Systems uses its own neutral white schema; it must not inherit the last
  selected system color.
- When a game is selected in All Systems, its platform-family logo and accent
  are used dynamically.
- Platform-family accent grouping and per-system accent grouping.
- Per-system grouping evenly distributes active systems through the hue wheel
  instead of using a fixed palette that clusters similar colors.
- Custom hue, saturation, and lightness editing for every active family or
  system target.
- Nintendo logo contrast handling must prevent a red accent from washing out a
  red logo.
- System hardware artwork uses real stock/official images, not AI-generated
  console images.
- Ambient system illumination comes from the top-right environment and must
  not form an outlined halo, oval, duplicate, or “ghost” around the console.
- Game wallpapers preserve aspect ratio, fill 16:9 by zoom/crop, and never
  stretch. Wider/narrower images should not be padded with blurred duplicate
  bands.
- If a real wallpaper cannot be found after the provider cascade, a true
  gameplay screenshot is allowed only as a tagged last resort.
- Missing wallpaper must never leave the previous game's wallpaper visible.

The importer writes `background-provenance.json` and uses explicit source tags
such as audited wallpaper, official gallery, LaunchBox fan art, and exact
gameplay screenshot. That provenance is critical: it lets a future desktop
audit identify screenshot fallbacks and replace them rather than merely seeing
that every game has “some image.”

Do not claim the media library is globally complete. The user has repeatedly
observed missing, mismatched, boxed-art-as-wallpaper, and incorrectly cropped
assets. The current pipeline is much safer, but the whole 4,000+ game library
still needs a final desktop audit rather than an expensive audit every app
launch.

### 4.5 Preview video behavior

Implemented behavior includes:

- Sound enabled by default, with a setting to disable it.
- Only the visible preview is audible; preloaded neighbors remain silent.
- Adjacent previous/next/auxiliary videos are sent to the preview service for
  preloading, avoiding a black flash on selection changes.
- A selected game's preview loops.
- A system-level random preview advances to another random game when the clip
  ends instead of looping the same clip forever.
- On the Thor, previews use the lower display during library browsing.
- On a one-screen device, preview video uses a top-right PIP positioned beside
  box art without covering list text.
- One-screen devices can swap the video and box-art positions.
- Preview placement can be Automatic, Lower Display, Top-Right PIP, or Off.
- The lower preview includes a translucent Play Now action that launches the
  previewed game in EmuFusion.
- During single-screen gameplay the lower Thor display is blank. During DS/3DS
  gameplay it becomes the actual lower gameplay surface.

Not every preview file has been quality-audited. Low-resolution or missing
videos should be replaced by higher-quality source files, and the older file
must be removed after verified replacement. Runtime upscaling was discussed but
is not a substitute for obtaining a better source and is not a qualified
feature.

### 4.6 Settings

The active settings sheet is paginated at six large rows per page rather than
cramming all controls onto one screen. Current options are:

1. System Wallpaper Mode — static, preloaded angle; the experimental moving
   decoder mode is disabled.
2. Game Preview Placement — automatic/lower/PIP/off.
3. Preview Video Sound — on by default.
4. Liquid Glass — optional and off by default.
5. Accent Color Grouping — by platform family or by system.
6. Customize Accent Colors — HSL editor.
7. System-Matched Stick LEDs — on/off.
8. Stick LED Brightness — manual 1–100%, default 2%.
9. Start View — Cover, List, All Systems, or a detected individual system.
10. Cover View Rows — one, two, or three; one row is the default.
11. Cover Row Order — reorders Systems and all seven library shelves.
12. Right Stick View Switching — on/off.
13. View Transitions — optional slide/fade/scale motion, off by default.
14. About EmuFusion — version, Pegasus credit, licenses, trademarks.
15. Update Library & EmuFusion — scans Downloads/library and checks GitHub.
16. PIP/Box Art Order — shown only on single-screen devices.

Liquid Glass is intentionally optional because the user disliked the earlier
distortion/readability tradeoff. Standard controls use the minimum darkening
needed for legible text and retain borders without distorting the wallpaper.

### 4.7 AYN stick LEDs

EmuFusion has a `ThorLedManager` that writes the same sysfs LED nodes used by the
installed AYN settings application. It scales RGB channels by the requested
brightness and reasserts the highlighted system color because stock controls
can restore their static white color on focus or power changes.

The visible settings separate enable/disable from brightness. They default to
enabled at 2%; the allowed manual range is 1–100%. Theme changes are debounced
to 12 ms and reasserted every 750 ms.

This feature is implemented but not fully release-qualified. Earlier user tests
saw white LEDs and brightness mismatches. The next hardware pass should verify
that the current package has the needed sysfs authority on a stock Thor, colors
change for every selected system, 1–2% is truly dim, disabling restores device
control, and the app does not fight the AYN system setting when backgrounded.

### 4.8 Library discovery and Downloads importing

`ImportManager` provides a conservative importer:

- Startup performs a lightweight, fingerprint-throttled scan of internal and
  removable-storage `Download` and `Downloads` folders.
- Manual maintenance performs a full storage/library discovery.
- The scanner searches common ROM/emulation roots across readable storage
  volumes and recursively identifies supported file extensions.
- ZIP and 7z archives are inspected. 7z extraction uses Apache Commons Compress
  with memory/entry-size limits and verifies the extracted result.
- Multi-file archives are deleted only after every recognized entry imported
  successfully.
- A source archive remains in Downloads if identification, extraction,
  destination write, registry write, or metadata publication fails.
- Candidate identity includes system and normalized game identity, so the same
  title on different systems is allowed. Deduplication must never be title-only.
- Region, revision, beta, date, dumper, and filename noise are removed from
  display titles while meaningful sequel/subtitle text is retained.
- Updates and DLC are not misidentified as base games.
- Android applications are explicitly disabled as a Pegasus provider and must
  never appear in All Systems as games.
- ROM records are durably published before slow media downloads, so an
  interrupted enrichment pass does not lose an imported game.
- Missing exact box art archives the item from the visual library instead of
  deleting the ROM. The archive list can include it manually.
- Rename changes metadata and the ROM filename with rollback on failure.
- Permanent delete stages the ROM, commits registry/metadata changes, then
  deletes; it rolls back if the filesystem operation fails.

The “audit all existing media” operation is deliberately not part of every app
startup. The user requested one-time audits to run on the desktop. Normal
startup should process new/changed Downloads and incomplete newly imported
records, not continuously rescan thousands of old assets.

### 4.9 Metadata and scoring

The intended scoring contract is:

- `CRITICS` and `USERS`, with no “MC” prefix.
- Values normalized to a 1–10 scale with one decimal place.
- When multiple sources exist, calculate a weighted composite using review/vote
  counts rather than averaging tiny and large samples equally.
- Release dates are stored separately from the large game title.
- Older systems need non-Metacritic sources and archived databases.
- Text metadata should eventually be shipped as a compact baked catalog so a
  newly imported retro game gets ratings/release data immediately.

Current code can emit normalized critic/user fields and preserve enriched
metadata across generated-file rebuilds. The historical library had many
ratings and dates, but the user later observed major gaps for NES, Genesis,
Game Boy, Game Gear, and SNES. Therefore the global baked-data requirement is
not complete. Do not claim “all games on all systems” are covered. A future
desktop job must reconcile preserved Thor data, source-specific caches, and the
catalog, then generate a versioned baked data artifact with matching tests.

### 4.10 Media enrichment

New imports can request:

- exact box art;
- true wallpaper/fan art;
- official gallery imagery;
- last-resort tagged gameplay screenshots;
- preview video;
- normalized title and text metadata.

Sources already represented in code/tools include official Nintendo gallery
assets, LaunchBox-style searches, Internet Archive/EmuMovies-style archives,
local curated packs, and the desktop retro-wallpaper-manager workflow. The
tools directory includes wallpaper manifests, live-wallpaper audit, blurred-
letterbox audit, contact-sheet generation, curated approvals, exact screenshot
fallback generation, deployment, and enriched-metadata recovery.

The required provider order is quality-first. A 1920×1080 image that merely
places box art in the center is not a wallpaper. Image dimensions alone cannot
detect that; visual/contact-sheet or image-model review is required. All
fallback types must keep explicit provenance.

### 4.11 Browser and downloads

The globe icon opens an in-app WebView. It:

- stays in the EmuFusion package;
- supports JavaScript, DOM storage, and site state;
- remembers the last location;
- hands downloads to Android `DownloadManager` in the public Downloads folder;
- allows downloads to continue after the browser view closes.

No ROM site is hardcoded. The user chooses the site. A completed download is
then eligible for the normal Downloads importer. Browser downloading had a
historical “failed to start” issue, so it requires an end-to-end device test
with a harmless downloadable fixture before release.

### 4.12 Updater

EmuFusion checks the GitHub release manifest at startup and on manual request.
When a newer app exists it should ask, download to a verified partial file,
verify/promote it, then open Android's installer confirmation. A regular
third-party Android app cannot silently replace itself; user confirmation is an
OS security boundary. Theme-only updates can be installed inside app storage.

The user previously experienced indefinite “checking” and “opening Android
installer” states. Current code resets stale in-flight status after process
death and reports errors safely, but a signed production updater flow has not
been fully acceptance-tested. The app must visibly show installed version and
turn setup/status steps green only after actual completion.

Do not upload the current qualification APK as the public latest release. It is
not production-signed or fully qualified.

## 5. In-process emulation architecture

### 5.1 Why the architecture exists

The earlier application launched standalone emulator APKs. That violated the
user's requirement because Android showed emulator menus, additional windows,
and extra recents entries. EmuFusion now owns the frontend API and emulator
surface itself.

The architecture separates engine implementation from user experience:

- `InternalEngineCatalog` maps normalized system IDs to an exact approved core.
- `LibretroHost` is EmuFusion's own minimal libretro frontend for software cores.
- `ExperimentalGlesLibretroHost` and `ExperimentalVulkanLibretroHost` own
  hardware-rendered core contracts.
- `LibretroEngineSession` handles software video/audio/input/state.
- `PpssppGlesEngineSession` is the common heavy/hardware session despite its
  historical name; it hosts more than PSP.
- `ExperimentalGlesRenderLoop` serializes surface, frame pacing, input, pause,
  context loss, and save calls on one render owner thread.
- `InWindowGameHost` covers the still-live library views with gameplay and
  later reveals the same library views.
- `InputRouter` maps Android devices to canonical console controls.
- `StateVault` writes Quick Resume and checkpoint snapshots atomically.
- `SecondaryGameplaySurfaceRouter` coordinates the same-package lower display.

Each core is pinned by source commit, source/archive hash, build recipe, exact
artifact hash, license record, firmware policy, state version, and renderer.
Qualification APKs contain explicit opt-in manifests and are denied by default.

### 5.2 Real-menu in-process launch bridge

Pegasus's Android command runner only accepts `am start` commands and its JNI
`MainActivity.launchAmCommand` normally calls `startActivity`. Even starting the
existing single-task Activity triggers pause/resume and Qt Surface recreation,
which exposed the EmuFusion startup splash and reset the selection on return.

EmuFusion keeps Pegasus-compatible `am start` metadata syntax but patches the
decoded `MainActivity.launchAmCommand` to call
`InProcessGameLaunchCommand.tryLaunch` first. The bridge:

1. accepts only EmuFusion's internal launch action;
2. requires EmuFusion's own MainActivity component;
3. validates the content/system/engine extras;
4. obtains the already-live MainActivity;
5. posts `InWindowGameHost.handleIntent` on that Activity's UI thread;
6. returns success before the original `startActivity` call.

This lets the real menu use its normal command path while producing zero
`ActivityTaskManager START`, zero `performResumeActivity`, and zero Qt
`createSurface` events.

### 5.3 Pinned frontend lifecycle patch

Upstream Pegasus assumes a successful external process launch and tears down
its QML engine/gamepad. EmuFusion's game is in-process, so that teardown would
destroy the exact menu state even though no Activity changed.

`unified-android/tools/patch_pegasus_in_process_launch.py` applies a fail-closed
byte patch to the exact pinned frontend ELF. At offset `0x75fd8`, the successful
launch subscriber is changed from frontend teardown/gamepad stop to:

- `ApiObject::onGameProcessFinished()` for provider/play bookkeeping;
- `ProcessLauncher::afterRun()` for launcher cleanup;
- return without deleting the QML engine.

The patch is checksum-locked to the expected input bytes and exact output
bytes. The APK verifier rejects upstream drift or a missing patch. This was
chosen because a matching local Qt 5.15.10 Android frontend build toolchain was
not available, while the pinned binary had stable, verified symbols and bytes.
A future full-source rebuild may replace the binary patch, but only if it
preserves the same exact lifecycle proof.

### 5.4 Saving model

Every game has one invisible Quick Resume snapshot plus a history:

- exit/held Stop flushes normal save RAM or memory cards first;
- serialized state includes engine ID/version, ROM hash, firmware fingerprint,
  checksum, active play time, timestamp, and screenshot;
- data is written to a temporary location, fsynced, validated, and atomically
  promoted;
- invalid/incompatible state is retained for recovery but not loaded;
- active play creates history checkpoints approximately every ten minutes;
- the newest 12 are retained, with older history thinned toward hourly anchors;
- target ceiling is 72 checkpoints or 512 MiB per game;
- the newest valid Quick Resume is never pruned.

ScummVM cannot use generic libretro serialization. Its Phase 2 route has a
Lucent-specific engine-native exit-autosave extension and must reject exit if a
safe slot cannot be committed.

### 5.5 Controller policy

EmuFusion normalizes D-pad, face buttons, shoulders, triggers, sticks, Start,
Select, guide/menu, touch, and motion. Known Android handheld and controller
profiles choose logical console mappings; unknown controllers receive a
capability-based fallback. On-screen controls are hidden on gaming handhelds or
when a complete physical controller is connected. They are a phone/tablet
fallback, not the normal Thor UI.

### 6.4 N64 work and current stopping point

N64 required three separate fixes:

1. **C++ runtime ABI failure.** The first Mupen core depended on a
   `libc++_shared.so` whose exported ABI did not match the core. Rebuilt with
   pinned NDK r27 static libc++, giving exact core SHA
   `fa0a07bb3d07cf61ae140099b6a90e6610a647e44d8e15d8d930ab18aa8c36a2`,
   no `libc++_shared` dependency, zero unresolved C++ ABI imports, and four
   16 KiB load segments.
2. **OpenGL negotiation failure.** Mupen's GLideN64 requests GLES3, depth, and
   `cache_context=true`. EmuFusion supported the lifecycle but did not advertise
   the advisory cache-context capability, so the core reported that the
   frontend had no OpenGL support. APK `818adab8…` advertises best-effort cached
   context and logs exact acceptance/reset/presentation markers.
3. **Held-Stop EGL/save race.** On `818adab8…`, real 007 gameplay rendered at
   about 60 FPS with audio and input. The library returned in 2 ms, but the
   gameplay TextureView was removed before the render thread paused. A queued
   swap hit an abandoned BufferQueue (`EGL_BAD_SURFACE`, `0x300d`), the session
   lost state-vault readiness, and Quick Resume did not commit.

The newest `cc15c076…` candidate fixes the third problem:

- `EngineSession.quiesceForExit()` was added.
- Software sessions synchronously pause through the host lock.
- Hardware sessions call `ExperimentalGlesRenderLoop.pauseAndWait()` while the
  TextureView Surface is still valid.
- The render-thread barrier drains earlier work, disables future scheduling,
  and pauses native rendering before any z-order/surface change.
- Warm Qt library views are brought above the retained, quiesced game root
  immediately, so visible return remains instant and the QML scene is not
  recreated.
- Background lifecycle work serializes and atomically commits Quick Resume,
  detaches EGL/audio/core, then removes the retired gameplay root.
- Late renderer errors during an already-stopping session cannot clear state-
  vault readiness, while save/commit still fails closed if serialization is not
  valid.

### 8.1 Phase 3 architectural rule

Phase 3 does not permit an external-emulator fallback in unified EmuFusion. A
native adapter must expose the same EmuFusion boundary as a libretro engine:

```text
probe -> load -> start -> pause/resume -> input/audio/video
flush persistent save -> serialize/restore if safe -> stop -> capabilities
```

The engine remains invisible to navigation. EmuFusion owns display surfaces,
pause UI, controller profiles, firmware validation, save identity, exit, and
the one app/window contract.

### 8.2 Wii U

Cemu is the candidate. Required work:

- establish a reproducible Android ARM64 build from pinned source/dependencies;
- implement a thin in-process adapter rather than opening Cemu's frontend;
- own Vulkan surfaces in EmuFusion;
- map TV output to display 0 and GamePad output/touch to Thor display 4;
- provide a single-screen layout for non-Thor hardware;
- validate user-supplied keys/firmware/content without bundling them;
- identify whether safe, deterministic state serialization exists;
- if reliable full state is unavailable, preserve normal game saves and make
  Quick Resume capability explicit rather than pretending it is safe;
- qualify controller, motion, audio, shader caches, surface loss, performance,
  and held-Stop lifecycle.

### 8.3 Switch

Eden is the tracked candidate. Required work:

- pin a stable release/source/dependency closure;
- audit GPL and inherited code/licensing;
- build the engine into the EmuFusion package with an in-process adapter;
- create a user-only firmware/key/NAND validation flow;
- never download or bundle keys;
- benchmark Vulkan driver compatibility and shader-cache lifecycle;
- determine whether a reliable state API exists. If not, held Stop can flush
  normal saves and exit, but may not claim full Quick Resume;
- qualify controller layouts, handheld/docked profiles, DLC/update discovery,
  storage, thermals, and compatibility.

### 8.4 PlayStation 3

The user specifically required aPS3e to be represented; it is real and tracked

- fail closed on unsupported titles rather than opening a separate frontend.

### 8.5 Vita, Xbox, Xbox 360, Windows, and 3DO

- Vita3K needs an Android-native adapter and state/firmware/license closure.
- xemu currently lacks a qualified Android ARM64 port and needs BIOS/HDD image
  handling plus a sustainable Vulkan/JIT path.
- Xenia needs a real Android ARM64 JIT/Vulkan route before UI integration.
- Winlator must be treated as a managed container engine, with per-game Wine/

  Quick Resume may need process/container suspension plus normal saves rather
  than emulator serialization.
- Opera/3DO is technically lower complexity, but its current non-commercial or
  license provenance is an immediate distribution gate. Choose a compatible
  replacement or obtain permission before integration.

### 8.6 Phase 3 definition of done

A Phase 3 system is complete only when it meets the same one-app, real-menu,
controller, save, return, legal, reproducibility, and exact-artifact gates as
Phases 1 and 2. “The emulator exists on Android” and “the source is open” are
not sufficient.

After runtime passes:

- finish transitive licenses, notices, corresponding source, and SBOM;
- remove unused legacy permissions such as package enumeration/process killing
  unless a current code path proves they are required;
- eliminate remaining visible Pegasus branding outside About/attribution;
- retain internal compatibility identifiers only where technically necessary;
- rebuild every native dependency for the required Android page size;
- choose a final application ID/version migration strategy;
- configure a production keystore and secure signing process;
- update `release-manifest.json` with immutable signed SHA values;
- test in-app update from the previous public release without data loss;
- publish source, source offer, licenses, theme ZIP, and signed APK together.

### Step 8 — only then begin Phase 3 implementation

Start with the candidate having the clearest legal Android in-process path.
Do not parallel-integrate every Phase 3 engine before the native adapter ABI,
surface lifecycle, firmware vault, state capability reporting, and one-window
test harness are proven on one engine.

## 12. Production blockers and risks

1. **Debug signing.** Qualification APKs are not public releases.
2. **Registry gates.** Phase 1/2 entries remain unqualified and unshipped.
3. **16 KiB compatibility.** Recent Lucent-built cores pass, but the whole Qt/
   frontend APK historically did not.
4. **License/SBOM completeness.** Phase 1 conclusions improved, but full
   transitive review—especially Phase 2—is open.
5. **Firmware.** Multiple systems remain deliberately blocked for lack of a
   legal, reproducible, hash-bound firmware route.
6. **State safety.** Loading a game is not proof that frequent serialization is
   safe, deterministic, or migration-compatible.
7. **Azahar runtime.** 3DS first-frame execution remains unresolved despite
   source-level dual-screen wiring.
8. **Dolphin final QA.** The frame-submit patch is built but current exact-device
   GC/Wii qualification is incomplete.
9. **Media completeness.** Ratings, dates, box art, wallpapers, and videos are
   not complete for all historical games.
10. **Updater UX/security.** Production signing, manifest trust, progress,
    installer handoff, and rollback need end-to-end testing.
11. **Permissions.** Legacy broad permissions must be removed or justified.
12. **Package identity.** `com.thorium.preview` enables upgrades but is not the
    final EmuFusion namespace. Migration must preserve data and updater behavior.
13. **Stale documentation.** Some older README passages still describe no cores
    in the default APK or historical external fallbacks. Treat the registries,
    exact artifact reports, this handover, and current source as newer authority
    and update stale docs before release.

## 13. Do-not-do list

- Do not edit the frozen theme/menu while finishing emulation.
- Do not directly launch a qualification Activity and call that menu proof.
- Do not start an external emulator and call it “internal.”
- Do not use RetroArch frontend code or UI.
- Do not suppress renderer/save errors merely to make Stop appear successful.
- Do not detach a GPU Surface before its render owner is synchronously quiesced.
- Do not delay visible return while compressing/saving if the surface can be
  retained safely behind the warm menu.
- Do not delete a source archive until every imported entry and registry write
  is verified.
- Do not dedupe games by title across systems.
- Do not let missing wallpaper display the previous game's image.
- Do not run a full media audit on every app launch.
- Do not bundle firmware, keys, commercial content, or unreviewed binaries.
- Do not publish a debug/qualification APK as latest.
- Do not overwrite an immutable QA candidate path; use a SHA-named copy.
- Do not reuse runtime evidence across different APK hashes.
- Do not mark `qualified` or `shipped` true to bypass a gate.

## 14. Final definition of done for EmuFusion

EmuFusion is ready for a public release only when one production-signed APK:

- installs over the prior version without data loss;
- starts as EmuFusion and shows the installed version;
- discovers legitimate ROMs without listing Android apps;
- imports ZIP/7z safely and enriches new games;
- provides complete, responsive Cover/List/System/All Systems navigation;
- preserves the frozen visual behavior or incorporates later user-approved UI
  changes;
- launches every advertised system inside the same EmuFusion MainActivity/window;
- maps controls correctly with no unwanted on-screen controls on handhelds;
- uses Thor display 4 correctly for DS/3DS and later Wii U;
- returns instantly to exact navigation state on held Stop;
- commits and restores valid Quick Resume without renderer races;
- maintains automatic history and normal in-game saves;
- passes performance, audio, frame pacing, thermals, surface loss, process
  death, reboot, and update migration;
- contains only approved, reproducible, correctly aligned native engines;
- ships complete licenses, notices, SBOM, corresponding source, and attribution;
- checks the signed GitHub release channel and performs a user-confirmed Android
  update reliably;
- passes the complete real-menu physical matrix against the exact released SHA.

Until those conditions are satisfied, call the build a qualification candidate,
not a finished Phase 1, Phase 2, Phase 3, or production EmuFusion release.
